# Подпись portable-обновлений

## Выпуск и границы доверия

Стабильный полный ZIP выпускается вместе с `RouteDeck-update.json` и
`RouteDeck-update.sig`. JSON описывает версию, Windows x64, точное имя ZIP,
размер и SHA-256 архива, а также каждый файл внутри: относительный путь,
размер и SHA-256. Хеши считаются по окончательным байтам ZIP. Дескриптор
расположен вне ZIP, поэтому нет циклического хеша. Подпись Ed25519 — ровно
64 двоичных байта над исходными UTF-8 байтами JSON, включая конечный LF.

1. `build-local-portable.ps1` собирает helper и updater с одинаковыми
   production features, считает их окончательные SHA-256, затем собирает GUI
   с обоими закреплёнными хешами. Повторная сборка или изменение этих бинарников
   после закрепления запрещены. Build manifest schema 3 содержит все три файла.
2. `package-controller.ps1` проверяет хеши и embedded pins, собирает полный ZIP
   из явного списка файлов и повторно проверяет скопированные байты.
   `write-update-manifest.ps1` создаёт bounded дескриптор полного стабильного ZIP.
3. Только tag workflow `release.yml` в `oda02/RouteDeck` получает секрет
   `ROUTEDECK_UPDATE_SIGNING_KEY` в одном шаге подписи. PR/build jobs его не
   получают. Секрет — PKCS8 PEM Ed25519; не передавайте его через аргументы,
   временные файлы, логи или артефакты. Скрипт проверяет соответствие публичному
   ключу клиента и использует [встроенный crypto Node](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptosignalgorithm-data-key-callback), без новых npm-зависимостей.
4. Publisher повторно проверяет подпись, SHA-256 ZIP и каждый файл, точный набор
   release assets и checksums, затем вызывает `gh release create --verify-tag`.
   Существующий выпуск и файлы не перезаписываются. Запусков `gh` и выпуска
   из fixture-тестов нет: они полностью подменены.

Секрет настроен отдельно с согласия пользователя; его значение не хранится в
репозитории. [Область доступа GitHub Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)
ограничена шагом подписи. Доверенная публикация тега означает доверие исходникам
этого тега и релизному workflow. Настройки защиты тегов и прав на выпуск остаются
ответственностью владельца репозитория.

Публичный ключ в `sign-update.mjs` и Rust должен совпадать; это проверяет тест.
Ротация требует заранее продуманного перехода доверия для уже установленных
клиентов. Простая замена ключа в следующем выпуске сделает обновление недоступным
старым клиентам. Authenticode, если появится, выполняется до хеширования и
подписи манифеста; он не заменяет Ed25519-проверку пакета.

## Bootstrap и ограничения

Первый выпуск с этим updater нужно скачать и распаковать вручную целиком.
Старые неподписанные portable-версии не приобретают доверенный механизм
обновления задним числом. Для установки клиент заранее скачивает подписанные
дескрипторы текущей и новой неизменяемых версий; текущая папка должна в точности
соответствовать подписанному списку. Изменённая папка или дополнительные файлы
переводят пользователя на ручное обновление в новую папку. Во время замены
сетевых запросов нет.

Автоматический механизм принимает только стабильные `x.y.z`; prerelease
продолжают распространяться как ручные ZIP без auto-update подписи.
SHA256SUMS включает дескриптор и подпись стабильного выпуска; сами checksums
не являются независимой подписью. Ключи и реальные релизы в проверках не
используются: криптотесты создают отдельный fixture key и проверяют байты,
подмену версии, подписи, ключа, путей и неизвестных полей. Publisher fixtures
проверяют реальные синтетические ZIP и прекращение работы до `gh` при ошибках.
